## 3. Категории и отсутствующие руки

Приоритет флопов: ВС → Aw → Ax → Dry → СС → НС → BBx → Bxx → xxx.

| Категория | Условие после исключения предыдущих | Досок |
|---|---|---:|
| ВС | Все три ранга T–A | 10 |
| Aw | A и две карты 2–5 | 6 |
| Ax | Остальные A-high | 54 |
| Dry | Оба соседних разрыва рангов ≥4, без A | 20 |
| СС | Старшая J–K, старшая − младшая ≤4 | 14 |
| НС | Старшая ≤T, старшая − младшая ≤4 | 34 |
| BBx | Средняя ≥T | 38 |
| Bxx | Старшая ≥T | 82 |
| xxx | Остальные | 28 |

Сумма — 286. Порядок показа: ВС, Dry, BBx, Bxx, xxx, СС, НС, Ax, Aw.
НВС = СС + НС; A = Ax + Aw, не тузовые ВС.

Руки: две пары+, оверпара, топ-пара, андерпара, вторая пара, weak,
третья пара, low pocket; затем непарные OESD, гатшот,
две оверкарты + БДФД, воздух. Двойной гатшот входит в OESD.
Отдельно сохраняем признаки БДФД и стрит-дро у пар.

`—` = нет рук с положительным весом в узле, не X, C или F.
Пример: weak-пары на ВС против BTN отсутствуют в полной таблице.
Нельзя сравнивать их с R/C против UTG как переход C → R/C только потому,
что C написан в базовой строке или HTML оставляет пустую поправку.

## 4. Веса: что именно усредняем

Для текущей версии берём исходные веса комбинаций в выбранном узле.
В экспортных таблицах это `reach_probability`. Не умножаем его повторно
на исходный префлоп-вес без доказательства, что такой множитель отсутствует.

Для набора комбинаций S и действия a:

```text
frequency(a | S) = sum(i in S, w_i * p_i(a)) / sum(i in S, w_i)
human_frequency(a | S) = sum(i in S, w_i * q_i(a)) / sum(i in S, w_i)
```

Исключаем reach≤0, но не солверные фолды и не отрицательные action EV.
Округляем только отображение; решения по порогам принимаем по точным значениям.

Это не простое среднее девяти процентов и не голосование по ярлыкам.
Исторический workbook использует другой порядок combo→board с равным весом досок:
его результаты не смешиваем с текущими reach-взвешенными частотами.

Отдельно показываем:

- частоту действия внутри категории — для игрового решения;
- вес категории в более широком узле — для оценки влияния упрощения;
- поддержку по доскам и комбинациям — чтобы не выдавать редкую клетку за общий закон.

При объяснении причины действия достаточно правильно исследовать саму категорию.
Её доля во всём нашем диапазоне не обязана засорять учебный разбор.
Но для оценки цены упрощения всей стратегии этот вес нужен.

## 5. Защита: как выбирали действия

### 5.1. Отменённая схема

В прежнем варианте встречались:

- перевод комбинаций в F при `max(EV_C, EV_R) − EV_F ≤0,02 bb`;
- последующий отбор продолжения и его нормировка до 100%;
- таблицы только с долей рейза среди продолжений.

Такие числа не показывали исходный полный F/C/R. Из «58% рейза среди
оставшихся продолжений» нельзя заключить, что вся исходная категория
рейзит 58%, или решить, что оставшуюся часть можно всю коллировать.

Не восстанавливать эту процедуру по старым архивам в текущих таблицах.

### 5.2. Принятый механический первый проход: 25/30/70

Сначала считаем исходные f, c, r всей клетки с её весами.

| Условие | Наше действие |
|---|---|
| Воздух или low pocket | F — явное пользовательское ограничение |
| f ≥25% | F |
| f <25%; r / (c+r) ≤30% | C |
| f <25%; 30% < r / (c+r) <70% | R/C |
| f <25%; r / (c+r) ≥70% | R |

R/C — строго 50/50. F проверяется первым.
Нормировка C/R здесь нужна только для выбора между C, R/C и R.
Она не удаляет исходный f из отчёта или оценки потерь.

Порог 25% — выбранный допуск к грубости стратегии, не свойство равновесия.
Он не доказывает равенство EV фолда, колла и рейза у каждой комбинации.

### 5.3. Как показываем результат

Верхняя строка — принятое действие. Нижняя — исходные F / C / R всей клетки,
а не частоты после нашего решения и не условные частоты продолжения.

Например:

```text
R/C
21 / 28 / 51
```

Значит: солвер F21/C28/R51; наша политика F0/C50/R50.
Здесь упрощение убирает 21 п.п. фолда, почти не меняя рейзы.
Округлённый ноль может скрывать малую исходную частоту.

## 6. Классификаторы защиты и их сокращение

### 6.1. Когда добавляли разделение

Для пар проверяем ДРО (гатшот или OESD), затем БДФД.
Для непарных гатшотов/OESD — БДФД, не само наличие дро.

Делим клетку на две наблюдаемые подгруппы, в каждой заново считаем
исходные частоты и применяем 25/30/70. Разделение разрешалось только
при разных устойчивых действиях. Сохранённые строгие зоны:

| Устойчивое действие | Условие в подгруппе |
|---|---|
| F | f >30% |
| C | f <20%; r/(c+r) <25% |
| R/C | f <20%; 35% < r/(c+r) <65% |
| R | f <20%; r/(c+r) >75% |

Это проверка устойчивости к независимым сдвигам порогов примерно на ±5 п.п.
Переход f=26% →24% сам по себе не оправдывает новый классификатор.
На границах и в промежутках оставляем действие исходной клетки.

Не более одного бинарного классификатора на клетку; без вложенных условий.
Воздух и low pocket не открываем обратно через классификатор.

### 6.2. Обозначения

| Защита | С признаком | Без признака |
|---|---|---|
| БД | C | F |
| БД/C | R | C |
| ДРО | C | F |
| ДРО/C | R | C |

БД в c-bet имеет **другое** значение: B с БДФД, X/B без него.
Обозначения не универсальны между ветками.

«БД: R; без: R/C» пользователь отдельно разрешил свести к R/C.
Не переносить это автоматически на «БД: R/C; без: F»:
там удаление условия меняет сам факт продолжения.

### 6.3. Автоматически проверяемое удаление малозначимых условий

Из двух действий сначала проверяли ближайшее к исходной общей доле
r/(c+r); если оно не проходит допуски — второе. Если оба не проходят —
сохраняли классификатор. Проверка аналитическая, не производственный генератор.

Для каждой комбинации:

```text
EV_old_i = sum(a, q_old_i(a) * EV_i(a))
EV_new_i = sum(a, q_new_i(a) * EV_i(a))
extra_loss_i = max(0, EV_old_i - EV_new_i)
```

Все EV в bb; исходные native EV в этих исследованиях делятся на 10.
Фолд имеет EV=0. Проверять единицы перед повторением.

| Дополнительная потеря от удаления условия | Сохранённый предел |
|---|---:|
| Взвешенное среднее внутри клетки | ≤0,02 bb |
| Вклад клетки во весь узел ответа BB | ≤0,02 bb на 100 решений BB |
| Взвешенный P99 внутри клетки | ≤0,10 bb |
| Максимум отдельной комбинации | ≤0,50 bb |

Все ограничения проверяются одновременно; улучшения на одних руках
не компенсируют ухудшения на других.

Исторически удалены 14 из 20 условий автоматически; две дальнейшие замены
приняты вручную. Для тех 16 замен MD сохранил дополнительные потери
0,0084 bb на 100 решений против BTN и 0,0059 против UTG.
Это **не аудит всей сегодняшней стратегии** и не цена последующих замен.

Пример ручной границы: третья пара UTG/Aw → C, средняя дополнительная потеря
0,0057 bb, P99=0,1013 bb. Это согласованное исключение, а не автоматический PASS.

## 8. C-bet: происхождение базы и уточнений

### История

Не было независимой стандартной таблицы, с которой «случайно совпал» солвер.
Взяли частоты BTN по всем флопам, усреднили по категориям рук с весами,
дискретизировали, отдельно учли БДФД — **так получили основу базы**.

Далее развернули её по девяти категориям флопов, приблизили действия к
локальным частотам, сравнили с UTG и вручную сокращали исключения.
При обратном сворачивании пользователь позднее выбрал **самое частое
действие**, не новый средний процент. Это отдельная операция.

Для дро текущий MD прямо фиксирует модальный выбор:
OESD — B в 6/8 непустых категорий, гатшот — БД в 7/9.
Доли веса рук под этими правилами: OESD 65% BTN /64% UTG,
гатшот 76% /83%. Это охват правилом, **не частота ставки**.

### Реализация действий

| Действие | Вероятность ставки на комбинации |
|---|---:|
| X | 0 |
| X/B | 0,5 |
| B | 1 |
| БД | 1 с БДФД, 0,5 без БДФД |

Поэтому частота БД в группе равна `0,5 + 0,5 × доля БДФД`, а не одной
фиксированной константе для всех клеток.

В старой версии 8 октября действовали включительные 30/70 и более подробные
подгруппы. Поздняя серия сравнивала доступные X/B, B, БД по фактической
взвешенной частоте и допускала небольшую ошибку ради общих правил.
Не придумывать один новый порог, будто он автоматически создал все текущие
ручные решения.

Для каждой замены сохранять:

- исходную частоту солвера и частоту старого/нового правила внутри клетки;
- вес клетки и вклад изменения в более широкий узел;
- если есть аудит EV — его отдельные показатели и хвосты;
- решение пользователя и точный охват изменения.

```text
delta_bet_node = weight(cell | node) * (new_bet_cell - old_bet_cell)
```

Равенство суммарной ставки не достаточно: перебет одних рук может
компенсировать недобет других. Проверяем по рукам, флопам, БДФД и подгруппам.

Пример из MD: гатшоты Aw, X/B → БД меняют ставку BTN на Aw на 1,75 п.п.,
но по всем флопам лишь на 0,033 п.п.; UTG — 0,34 и 0,006 п.п.
Это **влияние на частоту**, не потеря EV.

Ранговые советы «ниже ставят чаще» не включались автоматически в расчёт
50/50. Не обещать рассчитанную частоту стратегии, если исполнять микс
не рандомизатором, а другим непроверенным правилом отбора.

## 9. EV: как оцениваем цену, чего не утверждаем

Против сохранённой стратегии соперника и при сохранённой дальнейшей игре:

```text
candidate_EV_i = sum(a, q_i(a) * action_EV_i(a))
signed_loss_i = solver_mixed_EV_i - candidate_EV_i
clipped_loss_i = max(0, signed_loss_i)
mean_loss = sum(w_i * clipped_loss_i) / sum(w_i)
cell_contribution_per_100_node = 100 * sum(i in cell, w_i * clipped_loss_i) / sum(i in node, w_i)
```

Указываем базу сравнения: солвер, прежняя таблица или правило с классификатором.
Не подменяем смешанный EV солвера максимальным pure-action EV без отдельной метки.

- Равновесие выравнивает EV реально смешиваемых действий конкретной руки,
  с учётом точности решения; не все действия у всех рук и не средние категорий.
- Положительный средний EV колла не доказывает, что надо коллировать всю группу.
- EV чека не равен showdown equity против префлоп-диапазона.
- При наличии сохранённого EV чека/колла его можно сравнивать с другими действиями.
- Нет сохранённого показателя — сообщить пробел, не выводить его из equity.
- Локальный аудит не моделирует подстройку соперника, не равен exploitability
  и не доказывает оптимальность совместной игры двух упрощённых таблиц.
- Не складывать потери разных узлов как потери всей игры без общего reach.
- Следить за P95/P99, максимумом и массой отрицательных хвостов; среднее их скрывает.

## 11. Чего эта фиксация не делает

Не запускает солвер, не обновляет игровые действия, не коммитит сырые
STU005-выгрузки, не публикует курсы и личный префлоп-раздел.
Не превращает исторические цифры в новую проверку EV.
Сохраняет метод, проверяемые опорные примеры и границы выводов, чтобы следующий
анализ начинался с них, а не с восстановления по памяти.
